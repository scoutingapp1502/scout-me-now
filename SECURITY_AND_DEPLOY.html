01

The main / master split

git rev-list: 1287 vs 28 unique commits

origin/main and origin/master have diverged almost completely — main's recent history includes a commit literally titled "Elimat autentificarea" ("removed authentication"), which places it as an old, pre-auth line of work. master is where every session of work in this project has actually landed, including the pagination, story-sharing, and maintenance-mode features built most recently.

Most hosts (Vercel, Netlify, Cloudflare Pages) deploy from main by default. Left alone, that default would quietly serve the old, authentication-less main branch instead of the real app. The fix isn't to merge them — it's to tell the host explicitly which branch is truth.

Deploy from this one

master

Live, current. Every feature discussed in this project lives here. Point hosting at this branch explicitly in step 2 below.

Leave untouched

main

Old/abandoned line, pre-dates real authentication. Don't merge, don't delete yet — just make sure nothing deploys from it.

02

Hosting, step by step

Vercel or Netlify — both work the same way here

This is a static Vite build — no server runtime to provision. Any static host that builds from GitHub will do; Vercel and Netlify are the two with the least setup.

  1. Push the current work to master on GitHub

    Commit what's outstanding and push to origin master the normal way. Nothing special needed here — this is the branch the rest of the steps point at.

  2. Create the project on the host, from GitHub

    On Vercel: Add New → Project → Import Git Repository, pick scoutingapp1502/scout-me-now. On Netlify: Add new site → Import an existing project → Deploy with GitHub, same repo. Either will ask GitHub for permission the first time — that's a GitHub App install, not the token from your git remote.

  3. Set the production branch to master

    This is the step that fixes the main/master problem. On Vercel: Project Settings → Git → Production Branch, change it from main to master. On Netlify: Site settings → Build & deploy → Branches → Production branch, same change.

  4. Confirm the build command and output folder

    Both hosts auto-detect Vite, but verify: build command npm run build, publish/output directory dist. This matches package.json as-is — nothing to change there.

  5. Add the environment variables

    Before the first deploy, add the two VITE_ variables listed in the next section, in the host's dashboard — not in a committed file. See §3 for exactly which ones and why they're safe to expose.

  6. Deploy, then verify against master

    Trigger the first deploy. Once it's live, check the deployed commit hash shown in the host's dashboard against git log -1 origin/master locally — confirms it built from the intended branch, not main.

  7. Point the domain, if you have one

    Add the custom domain under the host's Domains settings; both Vercel and Netlify issue and renew the TLS certificate automatically once DNS resolves to them. Until then the host's own *.vercel.app / *.netlify.app URL works and is already HTTPS.

03

Environment variables

set in the host dashboard, not in git

Both of these already live in your local .env (gitignored). Copy the same values into the host's environment variable settings — they're meant to ship inside the built JavaScript bundle, so there's nothing to hide about them once deployed.

VITE_SUPABASE_URL

Your project's API endpoint. Public by nature — it's the address the browser talks to.

VITE_SUPABASE_PUBLISHABLE_KEY

The anon key. Designed to be public — every Supabase frontend ships it. Row Level Security, not this key's secrecy, is what actually protects data (§4).

Never add this one: the service_role key. It bypasses every RLS policy in the database. It belongs only in Supabase Edge Function secrets (already the case in this repo's supabase/functions/) — never in a VITE_ variable, which the browser can read.
04

Hardening the database

what actually limits blast radius on a breach

"Encrypting the database" isn't the lever most breaches turn on for a Supabase app — Supabase already encrypts data at rest and in transit. The real perimeter is Row Level Security (RLS): even if someone obtains the public anon key (trivial — it's in every page load) or finds a way to query the database directly, RLS decides row-by-row what they're allowed to read or write. This is the checklist for that perimeter, ordered by how much it moves the needle.

ControlStatus
RLS enabled on every table — confirmed across the migration set; nothing found open by default. Done
Admin role can't be self-granted — user_roles INSERT policy blocks role = 'admin', and no UPDATE/DELETE policy exists on that table at all. Done
Edge Functions verify the caller's JWT before using the service-role key, rather than trusting a client-supplied user ID. Fixed this session
Rotate the GitHub personal access token currently embedded in .git/config's remote URL — revoke it in GitHub → Settings → Developer settings, generate a new one, and re-set the remote without embedding it in the URL (use a credential manager or SSH instead). Your call — flagged, not yet actioned
Turn on 2FA on the Supabase account that owns this project — Account → Security. This is what actually stops "someone steals my admin password" from becoming "someone owns the database." To do
Never store a raw .sql export unencrypted — if you ever pull a manual backup, put it straight into a password-protected archive or delete it after use. Process habit

Where an admin role check matters, this is the pattern already used consistently in the schema — every admin-gated table checks the caller's role server-side, not just in the UI:

-- Standard shape used throughout supabase/migrations/
CREATE POLICY "Admins can update X" ON public.some_table
  FOR UPDATE TO authenticated
  USING (public.has_role(auth.uid(), 'admin'::app_role))
  WITH CHECK (public.has_role(auth.uid(), 'admin'::app_role));
05

Audit findings, this session

full pass across migrations, storage policies, edge functions

Two exploitable holes were found and fixed directly in code during this session. Two more are worth a look when there's time, but neither is an open door today.

Fixed · was critical

Scout document upload trusted a client-supplied user ID

Anyone who knew another user's UUID could overwrite that user's verification document and reset their approval status to pending — no login required. Fixed by deriving the user strictly from their own auth token instead of the request body.

supabase/functions/submit-scout-document/index.ts
Fixed · was high

Verification-decision emails had no caller check

The same missing-identity pattern let anyone trigger an "approved" or "rejected" notification email to an arbitrary user by UUID. Fixed by requiring the caller to hold the admin role before the function will act.

supabase/functions/notify-scout-verification/index.ts
Worth a look · medium

Chat attachment links don't expire on their own

Message and group attachment buckets are public storage with no per-viewer signature — anyone holding a specific attachment URL keeps access even after leaving the conversation. Paths are UUID-based, so not guessable, but not revocable either.

supabase/migrations/20260826110000_dm_message_attachments.sql
Worth a look · low

Invite-credit table has no ownership check on insert

A user can name themselves as inviter for any existing profile, fabricating invite credit that unlocks gated athletic tests. A business-logic integrity gap, not a data leak.

06

Staying safe going forward

habits, not one-time fixes

The pattern behind both fixed findings is the same one to watch for in any new feature: an ID arriving from the client is a claim, not a fact. Any new Edge Function or RPC that acts on a userId should pull that ID from the caller's own JWT, never from the request body — the same discipline already applied everywhere else in this schema via auth.uid() inside RLS policies.

Before adding a table that any signed-in user can write to, ask what a signed-in-but-unrelated user could do with it if the UI simply weren't there — RLS is the only thing actually enforcing the answer.
